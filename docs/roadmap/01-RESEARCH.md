# Research behind the feature roadmap

Four analyses run in parallel over the repository on 2026-08-23, before any of
[`00-FEATURE-PLAN.md`](./00-FEATURE-PLAN.md) was written. Each agent was told to read the
code and report findings rather than to propose features, and to distinguish what it
verified from what it inferred.

They are reproduced here largely as returned. The value is in the citations: every claim
in the plan can be traced from here to a file and a line. Where two analyses disagreed,
the plan followed the one that cited code.

The four questions were:

1. **Schema versus reachable surface** — what does the data model support that no
   endpoint or screen exposes?
2. **Infrastructure already paid for** — what is installed, or provisioned, and unused?
3. **The domain** — what does a vocational institute need that this does not have,
   grounded in the seeded trades rather than in generic LMS features?
4. **Decisions already made** — the ADRs, the cut list and the lessons, so the plan does
   not relitigate settled questions or reintroduce known bugs.

## Paragraphs on the most significant gaps

**TeacherProfile / StudentProfile — confirmed, and the gap is bigger than "no module."** They're not invisible: `auth.service.ts` includes and returns them on `/auth/me`, `users.service.ts` includes them on `GET /users`/`GET /users/:id` and even filters by `departmentId` through them (`users.service.ts:146-147`), and `departments.service.ts` counts them for `teacherCount`/`studentCount`. So there **is** a read path — what's genuinely absent is any write path. `createUserSchema` in `packages/shared/src/schema/user.ts:84-112` is fully built (email, role, departmentId, qualification, specialization, staffNo, enrollmentNo, with a `superRefine` requiring a department for non-admins and a qualification for teachers) but is deliberately never re-exported or routed — the `users.schema.ts` header comment states outright that there's no `user:create` action. `reinstateUserSchema` (`user.ts:129`) is in the same unwired state. Once a profile exists, `updateUserSchema` has no `qualification`/`specialization`/`staffNo`/`enrollmentNo`/`departmentId` fields, so it can never be edited either. Every TeacherProfile/StudentProfile row in the running system was created once, by `seed.ts`, and is permanently frozen.

**All three `searchVector` columns are pure dead weight, and the "why" is documented in the code itself.** Course, Resource, and Announcement each got a `GENERATED ALWAYS AS (...) STORED tsvector` column with a GIN index in migration 0002 — three separate columns, not the two the prompt named. All three service files carry near-identical comments admitting the substring search they actually ship ("v1 substring match") was chosen because reaching the tsvector needs raw SQL, which nobody wrote. The `fullTextSearchPostgres` preview feature is turned on in the generator block (`schema.prisma:14`) but nothing in the codebase exercises it — the columns aren't even declared in `schema.prisma` (migration 0002's own header note explains Prisma has no tsvector type and that `Unsupported("tsvector")?` was intentionally not added). This is the cleanest "column exists, nothing reads it" case in the schema.

**The Notification-creation pipeline doesn't exist at all — this is a bigger finding than any single unwritten enum member.** There is no `prisma.notification.create` call anywhere in `apps/api/src`; the entire feed a user sees is `seed.ts`'s fabrication. Concretely, approving/rejecting an enrolment, publishing a course or announcement, sending a message, and replying to a comment — the exact five real actions the enum's other seven values name — never produce a notification in a live system. The clearest smoking gun is in `enrollments.service.ts:449`, quoting policy documentation that promises "separate verb, separate audit action, separate notification" for a rejection — the audit half is real (the Prisma extension guarantees it), the notification half was never built. `ACCOUNT_SUSPENDED` is worse still: it's excluded even from the seed's fake data, so no row of that type has ever existed in this codebase.

**`AuditAction.RESTORE` and `.REINSTATE` are the audit-log mirror of the same problem, and the repo already says so.** `packages/db/src/audit.ts`'s `deriveUpdateAction` computes both labels correctly (deletedAt cleared → RESTORE; SUSPENDED→ACTIVE → REINSTATE), but neither transition is reachable: no `:restore` or `:reinstate` action exists in the policy `Action` union, and no route anywhere clears a `deletedAt` or reactivates a suspended user. `CourseDetail.tsx`'s delete-confirmation dialog (lines 991-1008) states this directly to the end user: "no endpoint exposes one, so putting the row back is a database change." Every other `AuditAction` value (CREATE/UPDATE/DELETE/LOGIN/LOGOUT/SUSPEND/APPROVE/REJECT/PUBLISH/MFA_ENABLE/MFA_DISABLE) is genuinely exercised by reachable code.

**Two stale `TODO(uploads)` comments quietly break a relation each, now that the excuse in the comment is no longer true.** Both `Course.syllabusUpload` and `User.avatarUpload` were designed around the uploads module before it existed, and neither call site was updated once it shipped. For the syllabus, the _write_ side works (`assertUploadClaimable` validates ownership on course create/update) but `toCourseDetail` hardcodes `syllabusUrl: null` unconditionally — a syllabus can be attached and can never be downloaded by anyone, and no screen even tries to render one. For the avatar it's worse: `updateSelf` actively rejects any `avatarUploadId` with a 422 ("Uploads are not available yet" — still asserted by a passing test), and `avatarUrlFor()` computes a DiceBear placeholder from the bare user id everywhere avatars are rendered, never consulting the relation even as a fallback check. Both are fully-modeled relations (`Upload.courseSyllabus`, `Upload.userAvatar`, `@@unique` FK columns) that are unreachable in both directions.

**Course and Department admin management is the largest gap between what the API serves and what a screen renders.** `POST/PATCH/DELETE /courses`, `POST /courses/:id/publish`, and `POST/PATCH/DELETE /departments` are complete, schema-validated, policy-gated endpoints — but grepping the entire web app finds no call to any of them. The only course-related mutation the SPA ever performs is a student's enrolment request. This means every writable Course field (`durationValue/Unit`, `capacity`, `startDate/endDate`, `description`) and every Department field is fully served for reading but has no UI path for writing at all — confirmed directly by `NEXT.md`'s own next-step note that admin CRUD for departments and courses is unbuilt, and today only Users has a screen. `GET /departments/:id` compounds this: it runs real aggregation queries for `courseCount`/`teacherCount`/`studentCount`/`description` and is never called by any page (`apps/web/src/lib/types.ts:68-71` documents this itself).

**Chat has three schema features nothing can trigger: message edit, message delete, and leaving a conversation.** `conversations.routes.ts` has exactly six routes and none of them updates or deletes an existing message, or removes/exits a participant. `Message.editedAt`/`.deletedAt` are serialized and filtered defensively but never written to a non-default value, and unlike comments (which do render "· edited"), `Messages.tsx` never reads `editedAt` at all. `ConversationParticipant.leftAt` is checked in roughly eight places as the definition of an "active" participant, and the add-participant handler even resets it to `null` when re-adding someone — but nothing ever sets it to a real timestamp, so once seated in a conversation, a user can never leave it.

**Settings.tsx has two more unwired affordances worth noting alongside the recovery-code stub already flagged in NEXT.md.** The "Turn off two-factor" button (`Settings.tsx:375-377`) has no `onClick` handler at all, and "Change password" (`Settings.tsx:399-401`) likewise has none — there is no authenticated change-password endpoint in `auth.routes.ts` at all, only the anonymous forgot/reset-password flow. Neither is a schema-field gap per se (no new model surface involved), but both compound the picture: MFA enrollment, MFA disable, and in-session password change are all promised by visible UI and none of the three actually functions.

## 2. Infrastructure already paid for

## Findings: paid-for, unwired infrastructure in Skillwright

### 1. socket.io + `@socket.io/redis-adapter` (apps/api) and `socket.io-client` (apps/web) — fully unused

**Declared:** `apps/api/package.json` (`socket.io: ^4.8.1`, `@socket.io/redis-adapter: ^8.3.0`); `apps/web/package.json` (`socket.io-client: ^4.8.1`).

**Verified unused:** `grep -rn "socket.io\|@socket.io"` across `apps/api/src` and `apps/web/src` returns zero real imports — only comments. `apps/api/src/app.ts` registers 13 Fastify plugins and 14 route modules; there is no `new Server(httpServer)`, no `io.use()`, no room/namespace code anywhere. `apps/web/src` has zero references to `socket.io-client`. The only places socket.io is mentioned are prose: a comment in `main.ts:21` ("onClose hooks in reverse registration order — socket.io and the queue workers...") describing a teardown order for a thing that isn't registered, and `redis.plugin.ts:13-14` noting that the adapter "must duplicate() this rather than reuse it" — advice for code that was never written.

**Intended for:** `docs/rebuild/00-REBUILD-PLAN.md` §6, "B+1 — Realtime depth" (lines 758-781), an explicitly optional post-ship increment (≈70h), not part of the shipped scope. Quoted: _"socket.io 4, authenticating from the same session cookie... Rooms `user:{id}` and `conversation:{id}`. The server never trusts a client-supplied room name, on any event... Today `typing_start`/`typing_stop`/`message_read` accept a client-supplied conversation ID and re-broadcast with no membership check whatsoever."_ Critically, the plan itself says the Redis adapter specifically should **not** be wired: _"Per-socket rate limiting... In-memory is fine at one machine; Redis and the socket.io Redis adapter are needed only if you run more than one Fly machine, and you will not."_ (line 776). And §7's cut list explicitly names `socket.io`'s dependency chain: Redis is one of the seven things under "Technology cuts... Roughly 90 hours and seven single points of failure" (line 834). So this isn't merely unused — it's infrastructure the plan itself said to avoid, that got installed anyway.

**What it would unlock, concretely, here:** Today, `apps/web/src/pages/Messages.tsx` polls — `conversations` query has `refetchInterval: 30_000` (line 87), the open thread's `messages` query has `refetchInterval: 15_000` (line 264). `NotificationBell`/`AppShell` don't poll at all: the unread-count query (`AppShell.tsx:111-114`) has `staleTime: 60_000` and no `refetchInterval`, refreshed only by manual `invalidateQueries` when the bell opens (`NotificationBell.tsx:125-130`) — a comment there documents that this already produced a visible bug (badge and panel disagreeing). Wiring socket.io would replace both polling loops with push and fix that class of staleness.

**Real cost:** Per the plan's own priority order — a `seq`-ordered `Message` schema change (`@@unique([conversationId, seq])`, `@@unique([senderId, clientMsgId])` — not present in the current schema, which has only `Message_conversationId_seq_idx` and `Message_senderId_idx`, no unique constraints), a reconnect/gap-backfill protocol, idempotent optimistic send, a rewritten `useWebSocket.ts`, membership-checked room joins, and a new failure surface: a WS server sharing the process, auth _inside_ `io.use()`, and (only if ever running >1 Fly machine) the Redis adapter and pub/sub fan-out. The plan is explicit that the adapter implies multi-process and is not needed at the current deployment target.

### 2. bullmq — fully unused

**Declared:** `apps/api/package.json` (`bullmq: ^5.34.6`).

**Verified unused:** zero occurrences of `bullmq`, `Queue(`, `Worker(`, or `QueueScheduler` in `apps/api/src`.

**Intended for:** §5's cut table (line 403) actually lists this as something to _cut_: _"BullMQ + Redis — two queues, one of which is 'send an email'. A promise you do not await plus a nightly cron covers both."_ — i.e., the plan's recommendation was never to add BullMQ at all. It survives only in the aspirational README diagram (see #5 below) and in `NEXT.md`.

**Concrete feature it unlocks, as the task flagged:** the abandoned-upload sweeper. `apps/api/src/modules/uploads/uploads.service.ts:104-108` states outright: _"NOTHING SWEEPS THE ABANDONED ROWS YET. A user who asks for a signature and then closes the dialog leaves a PENDING row forever, and upload.ts:87 already promises a cron that removes them. `@@index([status, createdAt])` (schema.prisma:418) is the index that job will read — it exists for exactly this and has no other caller today."_ `packages/shared/src/schema/upload.ts:87` carries the matching promise: _"Commit is the server's HeadObject checkpoint; an uncommitted upload is swept by cron."_ `NEXT.md:47` records the real-world consequence: _"the test suites... write into the same MinIO bucket as development, so it holds 83 objects backing two live resources. A sweeper needs BullMQ, which is a dependency nothing uses yet."_

**Real cost:** a `Queue`/`Worker` pair, a Redis connection dedicated to job state (separate from the rate-limit client per `redis.plugin.ts`'s own comment about not sharing a subscribed connection), a new process-lifecycle concern in `main.ts`'s shutdown sequence (which already gestures at "queue workers" that don't exist), and a decision about running the worker in-process vs. as a second deployed unit — which the single-machine Fly target in Appendix E does not budget for. The plan's own alternative — _"a promise you do not await plus a nightly cron"_ — is far cheaper and was the recommended path.

### 3. ioredis / the Redis service — partially used, but far short of what's declared

**Verified used:** `apps/api/src/plugins/redis.plugin.ts` creates one `ioredis` client, decorated as `app.redis`. Its only two consumers are `apps/api/src/plugins/ratelimit.plugin.ts` (global `@fastify/rate-limit` store + a hand-rolled per-account `INCR`/`EXPIRE` bucket) and `apps/api/src/routes/health.ts:23,27` (`/readyz` pings it). Session lookups go straight to Postgres — `apps/api/src/modules/auth/session.service.ts` calls `prisma.session.*` exclusively; there is no Redis session cache anywhere.

**Documentation overclaim:** `README.md`'s architecture diagram (lines 90-98) draws a `Socket.IO` box and a `BullMQ workers` box wired to Redis, and labels Redis `"sessions · rate limit · pub/sub · queues"`; the stack table (line 136) repeats it: _"Cache / queues | Redis 7 + BullMQ | Rate-limit store, session cache, Socket.IO adapter, and job queues."_ `docs/adr/0005-hand-rolled-sessions-over-vendor-auth.md:29` claims _"Redis caches it; correctness never depends on the cache"_ for session lookups — none of that caching exists. Only "rate-limit store" is real.

### 4. Full-text search infrastructure — tsvector columns + GIN indexes, unused by any query

**Declared:** `packages/db/prisma/schema.prisma:14,21` (`previewFeatures = ["postgresqlExtensions", "fullTextSearchPostgres"]`, `extensions = [citext, pg_trgm]`), materialized by raw SQL in `packages/db/prisma/migrations/0002_constraints/migration.sql`:

- Three `STORED GENERATED` `tsvector` columns (`Course.searchVector`, `Resource.searchVector`, `Announcement.searchVector`, lines 53-80) with matching GIN indexes (`Course_searchVector_idx`, `Resource_searchVector_idx`, `Announcement_searchVector_idx`).
- Six trigram GIN indexes (lines 84-90): `Course_name_trgm_idx`, `Course_code_trgm_idx`, `Resource_title_trgm_idx`, `Announcement_title_trgm_idx`, `User_name_trgm_idx`, `User_email_trgm_idx`.

The migration file's own header explains why: _"these columns are intentionally absent from schema.prisma (Prisma has no tsvector type)... `prisma migrate dev` will report them as drift."_ `citext`/`pg_trgm` are real extensions installed at `0001_init/migration.sql:14-16`.

**Verified unused:** every list query that filters by `q` — `apps/api/src/modules/courses/courses.service.ts:262`, `apps/api/src/modules/resources/resources.service.ts:301`, `apps/api/src/modules/announcements/announcements.service.ts:211` — uses Prisma's `contains`/`mode: 'insensitive'` (plain ILIKE substring), not raw SQL against `searchVector` or `similarity()`. Each site has an explicit comment admitting it, e.g. `courses.service.ts:262-264`: _"v1 substring match. The GIN tsvector index (`Course_searchVector_idx`) and the trigram indexes exist for a real ranked search, but `searchVector` is absent from schema.prisma on purpose... so wiring it needs raw SQL."_

**Intended for:** `00-REBUILD-PLAN.md:728` names "course catalog search" as one of five queries meant to be `EXPLAIN ANALYZE`'d in B6 (Hardening) to justify indexes with measurement — that hardening pass evidently produced this structure but the ranked-search consumer that would read it was never written.

**Real cost to wire:** one `$queryRaw`/`$queryRawUnsafe` call per search endpoint using `plainto_tsquery`/`ts_rank` (or `similarity()`/`%` for the trigram side), plus adding `searchVector Unsupported("tsvector")?` to `schema.prisma` per the migration's own note, or continuing to fight Prisma-migrate drift detection. Low risk relative to the other items — pure read path, no new process — but it's schema surface and write-path cost (every insert/update on `Course`/`Resource`/`Announcement` recomputes the generated column and maintains 9 GIN indexes) paid for zero ranking benefit today. Plain ILIKE substring matching gets _some_ incidental help from the trigram indexes at the planner's discretion, but the deliberate ranked-search design (weighted tsvector, `similarity()`) is completely dark.

## 3. Ranked recommendations

### 1. Attendance for practical sessions — **build, highest value**

- **User/job**: A workshop instructor needs to mark who was physically in the welding bay / at the lathe / on the rig today, per session, because presence is the thing being taught and assessed, not a side effect of it.
- **Why trade context raises the stakes**: In a lecture-based LMS, attendance is an engagement signal. Here it's closer to a compliance record — City & Guilds/NVQ-style awarding bodies (both named in the seed's `QUALIFICATIONS` list) gate assessment eligibility on minimum supervised contact hours, and safety/insurance sign-off for bay access depends on who was actually present. `Enrollment.status = APPROVED` currently answers "may this student be here" but nothing answers "was this student here."
- **What it builds on**: `Enrollment` is already the (student, course) unit of record; a satellite `AttendanceRecord{enrollmentId, sessionDate, status, markedById}` follows the same one-identity-table-plus-satellite discipline the rest of the schema uses, with the same explicit-`onDelete` rule. Policy-wise, `attendance:mark` (teacher `ownsCourse`, admin allow) and `attendance:read` (student `isEnrolledStudent`/self, teacher `ownsCourse`, admin allow) are near-zero new machinery — they reuse `ownsCourse` and `isEnrolledStudent` verbatim from `packages/shared/src/policy/combinators.ts`, composed the same way every other row in `docs/permissions.md` already is.
- **Cut-list collision**: none. It isn't grading (no assessment of work product, just presence), isn't analytics (a session register, not a chart), and doesn't touch roles, SSO, or realtime.

### 2. Prerequisites / progression gating — **build, cheap, strengthens the flagship claim**

- **User/job**: A student applying to "GTAW/TIG for Stainless and Aluminium" should be refused at request-time if they haven't completed "Shielded Metal Arc Welding: Level 1," instead of a teacher discovering the gap by eye and typing `decisionNote: "Prerequisite not met..."` by hand, as the seed literally does today (`seed.ts:692-693`).
- **Why trade context raises the stakes**: The course catalogue is already a level ladder by design (101/201/301 per department) — the domain assumes progression; the product just doesn't enforce it.
- **What it builds on**: `enrollment:request` is currently `isPublished` for a student (`docs/permissions.md` row `enrollment:request`). Adding a `hasCompletedPrerequisite` rule (checking the actor's own `COMPLETED` `Enrollment` rows against an optional `Course.prerequisiteCourseId` self-relation) and composing it with `and(isPublished, hasCompletedPrerequisite)` is the exact idiom `or(isPublished, enrolledApproved)` already uses in `combinators.ts`. This is a new provable rule in the generated, CI-checked permission matrix — it makes the project's own headline differentiator ("policy-as-data, generated matrix") _more_ provable, which is precisely the plan's own bar for what's worth building (§7's scope test).
- **Cut-list collision**: none.

### 3. Cohorts / course offerings (intakes) — **build if a phase can absorb the schema change**

- **User/job**: An admin needs to run "SMAW Level 1" again next term with a fresh 24 seats and a fresh roster, without last term's approvals, waitlist, and dates bleeding into the new run.
- **Why trade context raises the stakes**: Trade schools run repeating intakes (the product's own copy already says "spring intake" and "spring cohort" — `seed.ts:804`, `CourseDetail.tsx:980`); a university-style single-term `Course` row can't represent that.
- **What it builds on**: `Course` already carries every field an offering needs (`departmentId`, `teacherId`, `durationValue/Unit`, `capacity`, `approvedCount`, `startDate/endDate`) — this is a data-model correction (course template vs. offering, or a `code` family) more than new UI; the existing capacity-CHECK and enrollment machinery applies per-offering unchanged.
- **Cut-list collision**: none by name, but it's the one item here with real schema-migration cost, and a naive implementation risks becoming "just another screen" under the scope test if it ships as a new admin CRUD surface rather than a quiet model fix.

### 4. Workshop/equipment capacity as a second guarded number — **build the cheap version only**

- **User/job**: A CNC instructor needs "CNC Turning: Setup and Operation" capped at 10 because there are 10 working lathes, even though the admin's admissions capacity says 20.
- **Why trade context raises the stakes**: Trades are physically bound by machines and bays in a way lecture seats aren't; the seed's capacities (16–30) currently represent nothing but an admin's guess.
- **What it builds on**: This is the most direct reuse of the repo's own proudest mechanism — the `approvedCount <= capacity` CHECK-constraint pattern (`schema.prisma:328-333`) applied to a second bound. The cheap version is one more guarded column, not a subsystem.
- **Cut-list collision**: a full equipment/asset-inventory system (tracking individual machines, maintenance, serials) would read as scope creep into a different product and risks the "just adds another screen" test. **Do the guarded number, not the inventory system.**

### 5. Reporting/export for administrators — **build narrowly, as an export, not a dashboard**

- **User/job**: A department head needs a CSV enrolment/attendance register to hand an accreditor, not a chart to look at.
- **Why trade context raises the stakes**: The named qualifications (C&G, NVQ, CSWIP, F-Gas) are externally audited; the deliverable an inspector wants is a register, not a dashboard tile.
- **What it builds on**: `AuditEvent` (already admin-gated, append-only, `audit:read`) and `dashboard.service.ts`'s counting queries are exactly the machinery a CSV serializer would reuse — same Prisma queries, same policy gate, no new data model.
- **Cut-list collision — the closest call in this whole list**: the plan states outright, _"No analytics until B+2's audit events justify them — charting `COUNT(*)` is the canonical tell of a CRUD-only project."_ A reporting **dashboard** would be exactly that tell. Verified: no `.csv`/export code exists anywhere in `apps/` today — `AdminOverview.tsx` shows counts and a raw audit feed only. **Scope this as a plain "download roster as CSV" button, never a charts/analytics screen**, to stay on the right side of the plan's own tripwire.

### Minor, low-cost bonus: a completion "transcript" view

`Enrollment.status = COMPLETED` already exists and is seeded (`seed.ts:662-668`), but there's no `completedAt` timestamp (only `decidedAt`, which is really the approval date) and no screen surfaces "my completed courses" to a student. This is cheap and not cut — worth a line item, not a rank of its own.

## 4. What I would NOT build, and why

- **Certificates.** The plan says so in three words: _"No certificates."_ Even though `EnrollmentStatus.COMPLETED` exists, generating a certificate artifact (PDF, verification page, serial number) is explicitly forbidden. Stop at the data (`status = COMPLETED`); do not build the document.
- **A real timetable/scheduling engine** (recurring sessions, room/bay booking, clash detection, ICS export). Real value exists in principle, but it's a large net-new domain that barely touches existing schema (only `Course.startDate/endDate` as an anchor), doesn't extend either of the two provable-correctness claims (permissions, no-oversell), and is the textbook case the scope test is written to catch — "just adds another screen." If anything is worth doing here, it's a single free-text `Course.scheduleNote` field ("Tue/Thu 9am–1pm, Bay 3"), not a calendar engine. Treat true scheduling as a genuine v2 increment, in the same spirit as the plan's own deferred B+1/B+2 (realtime, audit-log UI).
- **A full equipment/asset-inventory subsystem** (per-machine tracking, maintenance logs, serials). The _capacity number_ is worth building (#4 above); the _inventory management product_ behind it is not — it's a different application wearing this one's login screen.
- **A "safety officer"/registrar role for PPE sign-off**, even though the seed's own placeholder copy gestures at PPE sign-off twice. This collides directly with the cut list's explicit line: _"No fourth role — a parent/coordinator/super-admin adds ~70 matrix cells for zero new insight."_ If PPE sign-off matters, fold it into attendance as a boolean on the session record, not a new actor in the permission matrix.
- **Any of the above as an analytics dashboard.** Repeated because it's the easiest one to drift into by accident: attendance stats, prerequisite-completion funnels, equipment-utilization charts are all one `COUNT(*)` away from the exact anti-pattern §7 names by name.

**Bottom line ranking**: build attendance (1) and prerequisites (2) first — they're cheap, they reuse the exact policy idiom already in `packages/shared/src/policy`, and neither is named in the cut list. Cohorts/intakes (3) and a guarded equipment-capacity number (4) are real but carry more schema cost and should be scoped tightly. A CSV export (5) is worth doing but only as an export, never a dashboard. Certificates, a full scheduling engine, an equipment-inventory system, and a new role are all things I would explicitly decline, three of them because the plan already declined them in writing.

## 3. Section 6 — Increments after the ship (already scoped, not new ideas)

Framed explicitly as **not phases** — self-contained, optional, entered by choice on a _live_ repository.

### B+1 — Realtime depth (≈70 h)

> "A chat that survives a tunnel — the one thing in this project a reviewer has not seen a hundred times." Revision 1 priced this at 44h and flagged it would overrun; the plan corrects to 70h as the honest number.

Build order given explicitly ("the first three are the story; the rest is garnish"):

1. Schema + sequencing — `Conversation`/`ConversationParticipant{userId, lastReadAt, leftAt}`/`Message{senderId, seq BigInt, clientMsgId}`, admins as ordinary participants (fixes the old schema's structural inability to seat an admin).
2. Reconnect with gap backfill via `conversation:backfill{id, sinceSeq}`.
3. Idempotent optimistic send via a client `clientMsgId` under `@@unique([senderId, clientMsgId])`.
4. Offline outbox in IndexedDB.
5. Presence/typing with TTL.

## 5. LESSONS-LEARNED constraints that bind any new-features plan

These are the entries that state a **rule**, not just a fixed bug — the ones a features plan has to carry forward or it reintroduces a bug this repo already paid for. Quoting the rule lines directly.

**Policy-matrix / subject-shape rules (the core cluster, #14, #15, #18, #31, #33):**

- **#14 — a check every route must pass belongs in the hook every route runs, not a helper most routes call.** _"Ask of any guard: what happens on a route that does not call it? If the answer is 'nothing', it is a convention, not a control."_ Any new provenance/status check (e.g. for a future actor state) must go in `onRequest`, not inside `authorize()`, or list routes that skip `authorize()` will silently ignore it — exactly what happened with `MFA_PENDING`.
- **#15 — a permission check with no subject denies everyone, silently, for any subject-dependent rule.** _"Before writing `can(actor, action)` with no subject, look up that action's rule for every role. If any of them reads a subject field, the call is a guaranteed denial."_ Applies to any new action added to the policy.
- **#31 — a `can()` call with the _wrong shape_ of subject denies exactly like one with no subject, and is harder to catch** because the call site looks correct. _"Before passing a subject to `can()`, check that the action's rules read fields that this kind of subject actually has."_
- **#18 — a subject-builder helper must never cast (`as unknown as PolicySubject`).** _"A cast in a shared helper is worse than a cast at a call site: it removes checking from every caller at once."_ Any new `subject()`-style helper for a new feature's policy subject must type-check field names, not cast past them.
- **#33 — a child object's own visibility flag can outrank its parent's.** _"When a child row carries its own visibility flag, ask whether reading the child directly bypasses the parent's gate."_ Directly relevant to any new child entity hanging off `Course`/`Announcement` (comments on a new type, attachments, etc.) — its own `isPublic`-style flag must be conjoined with the parent's publication state, not evaluated alone.

**The WHERE-clause-not-subject-gate rule for lists (#15 + #31, made explicit, reinforced by #28):**

> **#15:** _"Do not gate a **list** on a subject-free check, on either side. The server narrows rows with a WHERE clause mirroring the policy rows; the client simply runs the query."_
> **#31:** _"If the action is decided per row and you are gating a list, that is a category error and the answer is a WHERE clause, not a better subject."_
> **#28 (the enforcement mechanism):** _"When you notice an invariant spanning two files, a comment asking the next person to fix it is a wish. Make it structural (one exported function) or make it fail (a test that compares the two)."_ — i.e. any new list endpoint's visibility WHERE clause must be an **exported, imported** `visibilityWhere` function shared with anywhere else that needs the same filter (a dashboard tile, a count), never a second hand-copied clause.

Any new feature that adds a list/index endpoint must (a) never gate the list fetch itself on `can()` with a subject, (b) implement visibility as a mirrored WHERE clause exported from the owning module's service, and (c) add a test asserting the list total equals whatever other surface (dashboard, count badge) reads the same data.

**Citation rules (#34):**

> _"For a citation inside the same file, a line number is fine. Across files, name the **symbol** as well — `courses.service.ts`'s `viewerEnrollmentStatus` survives a reformat; `courses.service.ts:157` does not."_
> _"When you edit a file that others cite, `grep -rn "<filename>:"` for references to it. And re-verify after running a formatter."_

Applies to how a features plan itself should cite the current code — cross-file citations should name symbols, not just line numbers, since this doc's own citations will go stale the moment implementation starts.

**Other constraints worth carrying forward for any features plan:**

- **#38 (deployment artifacts / seams):** _"A deployment artefact is verified by running it and asking it questions, not by reviewing it."_ Any new feature touching the Docker image, env vars, or the static-file-serving path must be smoke-tested by actually starting the built container against a status/content-type/cache-control table, not just typechecked/linted — six of six faults were invisible to 977 passing tests.
- **#13 (transactions and second connections):** _"Never acquire a second connection while holding a transaction open — that includes anything a Prisma client extension, an ORM hook or a logging middleware does behind your back."_ Binds any new feature that writes an audit-adjacent side effect inside a service transaction (notifications, a new B+2-style extension) to use a dedicated connection pool, per the existing `auditPrisma` pattern.
- **#12 / #24 (Fastify body validation order):** _"Use `.nullish()`, never `.optional()`, for a Fastify body schema that is allowed to be absent"_ — and when fixed once, **grep for every route with the same shape**, not just the one that complained. Binds every new bodyless-POST route (approve/reject/suspend-style actions).
- **#29 (prototype-pollution via object-literal whitelists):** any new `sort`/`orderBy` whitelist must use `hasOwnProperty` or a `Map`, never a plain object indexed by user input.
- **#27 (cached identity outliving server-side revocation):** any new client-side cache of actor/session state needs a `QueryCache`/`MutationCache` error listener that drops the cache on `UNAUTHENTICATED`/`ACCOUNT_SUSPENDED`-shaped errors — a correct server-side guard is not enough if the client never re-asks.
- **#25 (error code vs. message):** the SPA renders by `problem.code`, never `problem.detail`; any new error path needs a **dedicated code and its copy added in the same change**, or the sentence is unreachable.
- **#26 (browser-driven review can invent defects):** _"Before reporting a UI defect, confirm it from a second, independent direction — query the API, read the element, watch the DOM over time."_ — relevant to how the three sibling agents' feature ideas should be _validated_ once built, not just proposed.
