# Screenshots

Every PNG under [`docs/screenshots/`](docs/screenshots/) is generated by driving the real
application. None is hand-taken, and that is the point.

## The problem this solves

Hand-taken screenshots go stale the first time a screen changes, and nobody remembers to
retake them — a README that shows a screen the app no longer has is worse than one that
shows no screen at all. So the captures live in a script, [`scripts/screenshots.ts`](scripts/screenshots.ts),
run with:

```bash
pnpm screenshots
```

One command re-signs in as each demo role, walks every screen, and overwrites the PNGs in
place. After a UI change, that is the entire maintenance step.

## How it works

1. **The staleness guard runs first.** Before any browser launches, the script globs every
   `.tsx` file under `apps/web/src/routes/` and checks it against two tables it owns:
   `ROUTE_CAPTURES` maps each route file to the capture(s) that show it, and `NOT_SCREENS`
   lists the files that render no screen of their own (layouts, the redirect-only `/`). Any
   route file in neither table — or any capture no route file asks for — exits 1 with the
   offending paths printed. A new screen without a screenshot is therefore a build error,
   not drift someone notices months later. The check needs no dev server, which is why it
   fails before the browser starts.
2. **One session per role, one login each.** Six browser contexts run in sequence:
   anonymous (the public forms and `/design`), student (light), student (dark), student at
   390px (one phone-width capture — mobile-first is a build constraint here, ADR 0008),
   teacher, and admin. Each signs in once through the real login form with the seed's demo
   credentials and then navigates, which keeps the whole run comfortably under the
   per-account login rate limit (`RATE_LIMIT_AUTH_ACCOUNT_MAX` in `.env.example`).
3. **Screens behind interactions are reached like a person reaches them.** The course
   detail opens by clicking a dashboard course card; the announcement detail by clicking a
   row in the announcements table; the message thread by clicking a conversation. The one
   exception is documented in the script: `/resources/:id` has no inbound link in the UI
   yet, so the shot discovers an id over the same-origin API and navigates by URL.
4. **Every navigation settles before the shutter.** `settle()` waits out the router's
   lazy-chunk spinner (a resolving route chunk is not a network event `networkidle` alone
   sees) and then the network going idle. Screens that fetch data in a mount effect also
   wait for a content marker — the table's first row, the thread's composer — because
   `networkidle` can be satisfied in the gap before the query even starts, which is how a
   skeleton once got photographed as `admin-users.png`.
5. **Each capture freezes animations** (`animations: 'disabled'`, so a Framer Motion
   transition never lands mid-flight) and overwrites `docs/screenshots/<name>.png` in place.
6. **One retry per session.** Dev servers under load occasionally drop a single request;
   the whole session re-runs before the script gives up on it.
7. **Exit codes.** `0` = every capture written. `1` = the coverage guard failed, or a page
   could not reach the state it was supposed to screenshot. Nothing is ever written
   partially without a non-zero exit.

## Prerequisites

- The Compose stack up (`pnpm infra:up`): Postgres on `:5433`, Redis, MinIO, Mailpit.
- Migrations applied and the seed run (`pnpm db:migrate && pnpm db:seed`). The seed is
  idempotent, so re-running it against a populated database is safe.
- The API on `http://localhost:4000` and the web dev server on `http://localhost:5173`
  (`pnpm dev` starts both). A different web origin can be pointed at with
  `SCREENSHOTS_BASE_URL`.
- A Playwright Chromium binary (`pnpm exec playwright install chromium`), once per machine.

## Adding a screen

Add the shot to the session whose role can see it, then list the capture name next to the
route file in `ROUTE_CAPTURES`. That is the whole ceremony — and if you forget either half,
the guard fails the run and names the file. If a route renders no screen of its own (a new
layout, a redirect), put it in `NOT_SCREENS` with the reason; the reason is the review.

## Troubleshooting

- **"Screenshots-coverage problem(s)" and nothing else ran** — the guard found a route
  file with no capture, or a capture no route requires. Fix the tables in the script; no
  server is needed to reproduce it.
- **Logins fail with 429** — the per-account login limit is 10 per 15 minutes and a full
  run signs the student account in three times. Wait the window out, or raise the limit in
  `.env` for the run.
- **Blank or near-empty PNGs** — the dev servers were down, restarting, or serving a stale
  module graph after source files changed underneath them. Confirm `http://localhost:4000/readyz`
  answers and reload `http://localhost:5173` in a normal browser; restarting the dev
  servers fixes a stale graph.
- **A capture shows an empty state** — check what the seed actually gives that role before
  assuming a bug. The teacher's enrolment-requests queue is the known case: the seed gives
  `demo.teacher@skillwright.dev` no pending requests, so the section renders its "Nothing
  waiting" state, and the capture says so honestly.
- **The gallery looks off in a way the seed does not explain** — the captures photograph
  whatever the dev database holds, including residue from browser testing. `pnpm db:reset`
  followed by `pnpm db:seed` restores the canonical data (destructive: it empties the dev
  database first).
